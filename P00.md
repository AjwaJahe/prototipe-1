## 3. Arsitektur sinkronisasi yang HARUS tetap utuh
Prinsip: **host otoritatif**. Client tidak dipercaya.

### A. Memulai sesi (`MultiplayerSession.gd`, autoload)
- Host memanggil `request_start_game` -> RPC `_rpc_start_game` ke semua peer -> semua pindah ke `res://main.tscn`. Meta tree `kelas_malam_multiplayer_active` dan `kelas_malam_is_host` dipakai script lain; jangan diganti namanya.

### B. `MultiplayerGame.gd` (node `MultiplayerGame` di `main.tscn`)
- **Pose pemain**: tiap `SEND_INTERVAL` (0,08 dtk) client mengirim posisi HANYA ke host (`_submit_player_state`, unreliable). Host memvalidasi (batas kecepatan, spawn awal, state terkunci host seperti hiding/KO/intro/capture) lalu menyiarkan (`_broadcast_player_state`). Avatar remote = `CharacterBody3D` proxy (grup `players`, meta `network_peer_id`); collider proxy MATI di client dan AKTIF di host.
- **Guru**: AI guru hanya jalan di host. Di client `Teacher.set_process(false)` dan `set_physics_process(false)`; posisinya mengikuti snapshot.
- **Snapshot dunia** (host -> client): `_send_world_snapshot(target_peer_id := 0)` setiap `WORLD_SYNC_INTERVAL` (0,2 dtk). Kunci snapshot: `game`, `teacher`, `players` (selalu dikirim) dan `doors`, `items`, `racks`, `hiding` (hanya entri yang BERUBAH, dibanding cache `_last_sent_world_sections`). Diterapkan di client oleh `_rpc_apply_world_snapshot`. Pintu dikirim per `MAX_DOORS_PER_WORLD_RPC` (8).
- **Pengaman 25 Okt 2026 (jangan dihapus)**:
  - Handshake: client memanggil `_request_full_world_sync()` -> RPC `_client_world_ready` ke host -> host mengirim snapshot PENUH khusus client itu (`_send_world_snapshot(sender_id)`) -> RPC `_full_world_sync_done` -> client set `_world_synced = true`. Client mengulang tiap 2 detik (maks. 10x) sampai dibalas.
  - Resync berkala: tiap `WORLD_FULL_RESYNC_INTERVAL` (6 dtk) host mengosongkan `_last_sent_world_sections`, sehingga semua pintu/item/rak/tempat sembunyi dikirim ulang penuh. Ini menutup kasus paket reliable hilang saat scene client belum siap.
  - Alasannya: snapshot delta yang hilang tidak pernah dikirim ulang tanpa dua mekanisme ini, dan itu membuat dunia host dan client berbeda terus-menerus.
- **Aksi gameplay** selalu lewat permintaan ke host, diputuskan host, hasilnya dikirim balik: `request_item_pickup`, `request_drop_item`, `request_door_interaction`, `request_rack_interaction`, `request_rack_store_item`, `request_hiding_interaction`, `request_board_*`, `request_penalty_answer`. Inventori pemain disimpan di host (`_peer_inventory_types`, `_peer_inventory_item_paths`).
- **Ping**: blok `# >>> HOST PING` ... `# <<< HOST PING` dan `_ping_probe`/`_ping_reply`.

### B2. Spawner item (`Map58ItemSpawnerV2.gd`, node `ItemSpawner`)
- Di sesi multiplayer HANYA host yang mengacak, menaruh, dan mengganti item. Pengecekannya `_is_network_client()` (meta `kelas_malam_multiplayer_active` aktif dan bukan server). Jangan dihapus dari: `_initialize`, `_randomize_initial_items`, `on_item_picked_up`, `request_item_respawn`, `spawn_item_at_location`, `_despawn_expired_ground_items`. Client menyembunyikan semua item sampai snapshot host datang (`_hide_all_items_until_host_sync`).
- Alasan guard `on_item_picked_up`: `PickupItem.on_picked_up()` ikut terpanggil di client saat pengambilan disetujui host; tanpa guard, client membuat klon "hantu" sendiri.
- Klon pengganti buatan host diberi meta `network_clone_of` (nama item sumber). Snapshot item membawa `clone_of`, dan client membuat klon bernama sama lewat `_create_network_item_clone()` di `MultiplayerGame.gd`. Nama klon (`<sumber>_Respawn_<ms>`) harus identik di host dan client; client tidak boleh membuat nama sendiri.
- Collision item di client disamakan dengan host lewat `_set_network_item_collision(item, not item.visible)` saat snapshot diterapkan (termasuk `CollisionShape3D`). Jangan kembali ke logika `_net_original_collision_layer`: item yang disembunyikan spawner lokal jadi tidak bisa diambil.
- `IntroQuestionPaper` SENGAJA dibuat per pemain di meja kursi spawn-nya oleh `Map58Game._prepare_intro_desk()`, jadi path-nya berbeda antara host dan client; itu bukan bug. Node `Held_*` di `FirstPersonViewModel/HeldItem` juga hanya tampilan lokal (collision-nya sengaja mati).

### C. Path node yang dipakai RPC dan `get_node_or_null`
RPC Godot mencocokkan NodePath di host dan client. Jangan rename, pindah parent, atau hapus node ini: `MultiplayerGame`, `Player/CharacterBody3D`, `Teacher`, `GameManager`, `WhiteboardController`, `SpawnManager`, node di grup `doors`, `map58_rack_storage`, `map58_hiding_spot`, `map58_classroom_cupboard`, dan node item ber-meta `item_type`.

### D. Aturan RPC
- Daftar RPC (nama, argumen, mode `@rpc(...)`) harus IDENTIK di host dan client. Menambah, menghapus, mengganti nama, atau mengubah argumen/mode RPC berarti SEMUA build (laptop/Windows dan APK Android) harus dibangun ulang bersamaan. Beri tahu user bila itu terjadi.
- Jangan mengubah `authority` / `any_peer` / `reliable` / `unreliable` tanpa alasan dan tanpa tes dua peer.

### E. Chat dan suara (`MultiplayerCommunication.gd`)
- Suara: mono PCM16 16 kHz, paket 320 frame, RPC `unreliable_ordered` channel 1, diteruskan lewat host (`_relay_voice`). Host juga memberi tahu guru (`hear_multiplayer_voice`). Jangan ubah format paket tanpa mengubah pengirim dan penerima sekaligus.

## 5. Cara memperbaiki lag dengan benar
1. **Ukur dulu**, jangan menebak: Godot Profiler (Debug -> Profiler), `debug\profile_scripts.gd`, `diagnostics_performance_20261006\PerfProbe.gd`. Catat FPS dan script teratas sebelum dan sesudah.
2. **Kandidat yang terlihat di kode** (BELUM terbukti sebagai penyebab lag; buktikan dengan profiler):
   - Host: `_build_world_snapshot()` jalan tiap 0,2 dtk dan menelusuri seluruh pohon scene (`_collect_item_snapshot`), mengambil grup pintu (+ `_collect_door_transforms` rekursif per pintu), rak, tempat sembunyi, lalu `duplicate(true)` per section. Optimasi aman: simpan cache daftar node sekali saat dunia siap dan segarkan seperlunya, dengan isi snapshot dan format RPC TETAP sama.
   - `MultiplayerCommunication._wall_occlusion`: sampai beberapa raycast per peer tiap 100 ms. Boleh dinaikkan intervalnya atau di-cache.
   - Raycast/pencarian target di `TeacherAI_New.gd` (lihat juga `PROMPT_1_OPTIMIZE_TEACHERAI.md`).
3. **Teknik yang DIIZINKAN**: cache referensi node, throttle raycast, hindari alokasi berulang tiap frame, kurangi pekerjaan berulang di host, kurangi log.
4. **Teknik TERLARANG** (merusak sinkronisasi): menghapus section snapshot; mematikan handshake atau resync 6 dtk; memindahkan otoritas ke client; menghapus validasi posisi/inventori di host; mengubah mode `@rpc`; menurunkan data penting ke unreliable tanpa tes; mematikan avatar proxy atau collider proxy di host; mengubah path node.
5. Setelah tiap optimasi, pastikan kunci dan isi dictionary snapshot (`game`, `teacher`, `players`, `doors`, `items`, `racks`, `hiding`) tidak berubah. Kalau harus berubah, umumkan dulu ke user.

### 9.3 Fakta `RoomFlow.gd` (dibaca 26 Okt 2026, 555 baris)
- UI dibuat lewat kode: `_show_home`, `_show_setup`, `_show_join`, `_show_lobby`, dengan helper `_add_title`, `_add_body`, `_add_button`, `_add_field_label`, `_clear_content`.
- Alur NodeTunnel: `_begin_connection(action, code)` memeriksa `ClassDB.class_exists("NodeTunnelPeer")`, lalu `connect_to_relay(NODETUNNEL_RELAY, NODETUNNEL_APP_ID)`, lalu `multiplayer.multiplayer_peer = _peer`, lalu sinyal `authenticated` memicu `host_room`/`join_room`, lalu `room_connected` memanggil `_on_room_connected` yang mengisi `_room_id`, `_is_host`, dan menampilkan `_show_lobby()`.
- Lobi bergantung pada `_room_id` tidak kosong (`visible and not _room_id.is_empty()`). Host menyimpan status siap di `_ready_by_peer` (host = peer id 1) dan menyiarkannya lewat `_broadcast_lobby_state()`.

- Penolakan kapasitas di `_on_player_connected` memakai `peer.call("disconnect_peer", peer_id, true)`; `ENetMultiplayerPeer` punya `disconnect_peer(id, force)`.
- `export_presets.cfg` Android sudah `permissions/internet=true`.

### 9.7 Panduan pengguna: host lewat playit.gg (UDP)
Ringkasan dari situs playit.gg; tampilan situs bisa berubah, cocokkan dengan halaman resminya.
1. Buat akun gratis di playit.gg, pasang program agent playit di PC host, beri nama agent.
2. Di dashboard pilih "Create Tunnel": protokol UDP (kustom), port lokal 7777 (sama dengan `DIRECT_DEFAULT_PORT`). Menurut situs, tunnel gratis memakai "Global Anycast" (rute tidak selalu optimal), memilih region khusus butuh Premium (situs menyebut sekitar $3 per bulan), dan jumlah port gratis dibatasi 4.
3. Playit memberi alamat publik berbentuk `nama.at.ply.gg:PORT`. Host menjalankan game, memilih "BUAT ROOM LANGSUNG", mengisi alamat publik itu pada kolom opsional, lalu membagikannya.
4. Pemain lain memilih "GABUNG LANGSUNG" dan memasukkan `nama.at.ply.gg:PORT`.
5. Cek rute: buka `http://ping.gl.ply.gg` dari tiap pemain; kolom `tunnel_name` menunjukkan datacenter yang dipakai. Bila bukan Singapura dan ping tinggi, pertimbangkan tunnel regional (Premium).
6. Host sebaiknya memakai koneksi kabel atau WiFi yang stabil.
